## 1. 결론

두 소스는 **동일한 논리 스키마**다. 공통 테이블 32개에서 컬럼 구성 차이는 `SELF_DB` 하나뿐이며,
이 컬럼은 신규 체계에서 폐기되므로 이관에 영향이 없다.

따라서 **소스가 어느 쪽이든 본 매핑표가 그대로 적용된다.**

## 4. 암호화 범위 차이 — **주의**

두 소스의 암호화 적용 범위가 다르다.

| 테이블 | 컬럼 | Oracle 타입 | MsSQL 타입 | 구분 |
|---|---|---|---|---|
| ACTIVE_SONAR | SONAR_NAME | VARCHAR2(100 BYTE) | varbinary(300) | MsSQL만 암호화 |
| ACTIVE_SONAR | SONAR_NAME_ISUS90 | VARCHAR2(100 BYTE) | varbinary(300) | MsSQL만 암호화 |
| CLASSES | CLASS_NAME | RAW(200) | varbinary(300) | 양쪽 암호화 |
| CLASSES | CLASS_NAME_ISUS90 | RAW(200) | varbinary(300) | 양쪽 암호화 |
| CLASSES | CLASS_NAME_K | RAW(200) | varbinary(300) | 양쪽 암호화 |
| TRANSIENT | TR_NAME | VARCHAR2(200 BYTE) | varbinary(300) | MsSQL만 암호화 |
| VESSEL_DATA | VESSEL_NAME | RAW(200) | varbinary(300) | 양쪽 암호화 |
| VESSEL_DATA | VESSEL_NAME_ISUS90 | RAW(200) | varbinary(300) | 양쪽 암호화 |
| VESSEL_DATA | VESSEL_NAME_K | RAW(200) | varbinary(300) | 양쪽 암호화 |

- **MsSQL** : `ENCRYPTBYKEY` (대칭키 `symmetric_key_AASManager`, 인증서 `certificate_manager`).
  2026-07-22 복호화 검증 완료. 이관 계정에 아래 권한 부여가 전제다.

  ```sql
  GRANT VIEW DEFINITION ON SYMMETRIC KEY::symmetric_key_AASManager TO <이관계정>;
  GRANT VIEW DEFINITION ON CERTIFICATE::certificate_manager TO <이관계정>;
  GRANT CONTROL        ON CERTIFICATE::certificate_manager TO <이관계정>;
  ```

- **Oracle** : `RAW(200)`. `ENCRYPTBYKEY` 와 규격이 다르며 **복호화 방식이 확인되지 않았다.**
  소스로 Oracle을 채택할 경우 선결 과제다. (05 문서 참조)

## 5. 타입 변환

| Oracle | MsSQL | 처리 |
|---|---|---|
| `VARCHAR2(n BYTE)` | `varchar(n)` | 동일 |
| `CHAR(n BYTE)` | `char(n)` / `varchar(n)` | 동일 |
| `NUMBER(*,0)` | `int` | 동일 |
| `NUMBER(p,s)` | `float` / `decimal` | 동일 |
| `NUMBER` (무정밀도) | `int` / `float` | 값 범위 확인 후 결정 |
| `DATE`, `TIMESTAMP(6)` | `datetime2` | 동일 |
| `RAW(n)` | `varbinary(n)` | 암호화 컬럼 — 위 참조 |
