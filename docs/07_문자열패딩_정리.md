| 항목 | 내용 |
|---|---|
| 문서번호 | NAIMS-MIG-260820-07 |
| 작성일 | 2026-08-20 |
| 대상 DB (Dev) | 192.168.200.205:1433 / NAIMS2 — **적용·검증 완료** |
| 대상 DB (Testbench) | 10.1.1.10 / NAIMS2 — **미적용**(폐쇄망, 개발 PC 에서 접근 불가) |

## 1. 증상과 원인

분석관단말기 `식별자료 관리 > Active Intercept` 에서 이관 레코드의
`능동소나 종류 / 송신방식 / 변조방식 / 송신모드` 가 가운데정렬을 벗어나 왼쪽으로 밀려 보였다.

UI 결함이 아니다. WPF `TextBlock` 은 **후행 공백을 DesiredSize 폭에 포함**하므로,
값이 공백 패딩되어 있으면 `HorizontalAlignment="Center"` 가 "공백 포함 문자열" 기준으로 정렬한다.

```
"ASW"                    → desiredWidth  25.86 px
"ASW                 "   → desiredWidth  97.60 px   (셀 가용폭 100px 를 거의 다 차지)
```

원인은 **레거시 고정길이(`char(N)`) 값을 `TrimEnd` 없이 그대로 INSERT** 한 것이다.
`char(N)` 컬럼은 값이 짧으면 DB 가 공백으로 채워서 돌려주고, SQL 의 `=` 비교는 후행 공백을
무시하므로 **쿼리로는 멀쩡해 보인다** — 화면에서만 드러난다.

오염은 두 종류다.

| 유형 | 모습 | 파급 |
|---|---|---|
| A. 값 + 후행 공백 | `'ASW' + 공백 17` | 화면 정렬 붕괴, `LIKE`·`GROUP BY` 오동작, Export 오염 전파 |
| B. 공백만 저장 | `TRANS_TYPE = 공백 20` (NULL 도 `''` 도 아님) | `IS NULL` / `= ''` 필터가 전부 빗나감 |

문자열이 NAIMS2 로 들어오는 경로는 두 프로그램, 네 갈래다.

| # | 프로그램 | 경로 | 문자열 출처 | 조치 |
|---|---|---|---|---|
| 1 | RawCollectMigrator | DB→DB 이관 (`DbToDbExecutor`) | 레거시 Oracle/MsSQL `char(N)` 컬럼 | 소스 읽기 지점에서 정규화 |
| 2 | RawCollectMigrator | 수집자료 이관 (`Collection/MigrationExecutor`) | DMF·ALG 파일(고정폭) | 문자열 절단 헬퍼가 정규화 경유 |
| 3 | RawCollectMigrator | 원시자료 추출 (`ExtractRaw/ExtractMigrationExecutor`) | `.SPS`/이벤트목록(고정폭 바이너리) | 문자열 절단 헬퍼가 정규화 경유 |
| 4 | DBImplant_N1toN2 | 단주기 패키지 적재 (`SdPackageImporter`) | `.SD`/`.CLA`/`.TMP` (C 고정 배열) | 실행 직전 파라미터 일괄 정규화 |

> `SdPackageImporter` 가 `TRM_MODE`·`MODULATION`·`SONAR_NAME` 등을 직접 쓴다.

### 정규화 헬퍼 (단일 창구)

땜질을 INSERT 문마다 붙이지 않는다 — 한 군데만 빠뜨려도 오염이 되살아나고,
그때의 증상은 "화면 정렬이 미묘하게 틀어지는 것"뿐이라 몇 달 뒤에나 발견된다.
그래서 규칙을 **한 파일**에 두고 모든 값이 그곳을 지나게 했다.

- `RawCollectMigrator/Infrastructure/LegacyText.cs`
- `DBImplant_N1toN2/Infrastructure/Utilities/LegacyText.cs` (같은 규칙)

```csharp
public static readonly char[] TrimChars = { ' ', '\0' };
public static string  Normalize(string? s);        // null → ""
public static object? NormalizeValue(object? v);   // 문자열만 정규화, 나머지는 원본 통과
public static void    NormalizeStringParameters(DbCommand cmd);   // 실행 직전 일괄
```

### 경유하도록 바꾼 지점

| 파일 | 지점 | 역할 |
|---|---|---|
| `DbToDbExecutor.ReadSourceRowsAsync` | 소스 행 읽기 | **소스 값이 도구 안으로 들어오는 유일한 문.** 여기서 떼면 INSERT·dedup 대조·자연키 재사용·미리보기가 모두 같은 값을 본다 |
| `DbToDbExecutor.SeedReuseAsync` | 자연키 (PK, 키) 목록 | 별도 읽기 경로. 정규화 없으면 `"ASW␣␣"` ≠ `"ASW"` 로 잡혀 중복 INSERT |
| `DbToDbExecutor.ConvertScalar` (varchar 분기) | 타입 캐스팅 | 소스를 거치지 않은 문자열(고정 기본값·규칙 산출값)도 덮는다. **절단 전에** 정규화 |
| `DbToDbExecutor.ExecInsertAsync` | INSERT 파라미터 바인딩 | 타겟으로 값이 나가는 마지막 문 — 값 결정 분기가 늘어도 우회로가 생기지 않는다 |
| `DbToDbExecutor.OverwriteAsync` | UPDATE 파라미터 바인딩 | 사람이 해결 창에 직접 입력·붙여넣기한 값도 포함 |
| `DbToDbExecutor` dedup 키 대조 | `TrimEnd` → `LegacyText` | 대조 규칙도 한 곳에서만 정한다 |
| `CryptoContext.ResolveValue` | 복호 결과 / 외부 이름표 | 복호 결과도 소스 `char(N)` 폭만큼 공백이 붙어 온다 |
| `Collection/MigrationExecutor.Truncate` · `TruncateText` · `TruncateRight` | 문자열 절단 | 자르기 전에 떼야 폭을 패딩으로 낭비하지 않는다 |
| `ExtractRaw/ExtractMigrationExecutor.Trunc` | 문자열 절단 | 위와 같음 |
| `SdPackageImporter` (5개 지점) + `.Detections` (3개 지점) | 실행 직전 | 파라미터가 늘어도 자동으로 덮인다 |

### 자체 검증 단계 (재발 방지)

`DbToDbExecutor.VerifyNoStringPaddingAsync` 를 **커밋 직전, 같은 트랜잭션 안에서** 실행한다.
이번 실행이 넣은 행까지 보이며, 1건이라도 걸리면 예외를 던져 **커밋하지 않고 롤백**한다.
`DbToDbOptions.VerifyStringPadding` 으로 끌 수 있다(기본 켬).

커밋한 뒤에 확인하면 이미 오염이 남은 것이고, 그때는 백필 말고 되돌릴 방법이 없다.

## 3. 결정된 정책 (2026-08-20)

| 항목 | 결정 | 근거 |
|---|---|---|
| 빈 값의 표준 표현 | **`''` (빈 문자열)** | NAIMS2 의 `STD_*` 문자열 컬럼 130개 중 **97개가 NOT NULL** — NULL 로는 통일 자체가 불가능하다. 두 표현이 섞이면 검색 조건이 `IS NULL` 과 `= ''` 를 둘 다 봐야 하고, 한 쪽을 빠뜨리는 순간 조용히 틀린다 |
| 선행 공백 | **건드리지 않음** (`RTRIM` 만, `LTRIM` 없음) | `COMMENT`·`*_RMKS` 는 자유 입력 필드라 사용자가 의도한 들여쓰기일 수 있고, 실측상 진짜 선행 공백 데이터는 0건이라 얻을 것이 없다 |
| `'-'` 플레이스홀더 | **그대로 보존** | 레거시 작성자가 "없음"이라고 **판단해서 적은 값**이다. 빈 값으로 바꾸면 "입력 안 함"과 구분이 사라지고 되돌릴 수 없다. Dev 실측 `STD_ACTV_SONAR.TRM_MODE` 9건, `STD_PULSES.TRM_MODE` 23건 |
| 패딩 문자 | 공백(0x20) + NUL(0x00) | NUL·TAB 오염은 실측 0건. NUL 은 C 고정배열 방어로 넣되 비용이 없다. SQL `RTRIM` 과 규칙을 일부러 맞춰 두었다 |

- 먼저 `backfill_trim_padding.sql` 상단의 `@WhatIf = 1` 로 대상만 보고 싶으면 그렇게 한 번 돌린다.
- 백업은 `@DoBackup = 1`(기본)이면 자동으로 `_bak_YYMMDD` 가 생긴다. 같은 이름이 이미 있으면 덮지 않는다.
- 스크립트는 **전체 테이블을 실측으로 훑으므로** Dev 와 Testbench 의 데이터 차이에 영향받지 않는다.

## 7. 재발 시 확인 순서

1. `verify_padding.sql` — 어느 테이블·컬럼에 몇 건인가.
2. 이관 프로그램 로그에서 `✔ 문자열 패딩 검증 통과` 줄을 찾는다.
   없으면 검증이 꺼졌거나(`VerifyStringPadding=false`) 그 버전이 아니다.
3. 있는데도 오염이 있다면 **이관 이후에 다른 경로가 쓴 것**이다 — 2절 표의 4개 경로 밖을 의심할 것.

> ⚠ 검출에 `LEN(c) < DATALENGTH(c)` 를 쓰지 말 것. varchar 에 든 한글은 1글자가 2바이트라
> 정상 데이터가 대량 오탐된다. 반드시 `DATALENGTH(RTRIM(c))` 와 대조한다.
> ⚠ 유형 B 는 `col = ''` 로 찾을 수 없다. SQL 의 `=` 비교가 후행 공백을 무시하기 때문이다.
> `DATALENGTH(c) > 0 AND LEN(c) = 0` 을 쓴다.
