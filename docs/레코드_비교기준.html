1. 두 가지 비교 방식

방식짝짓는 근거언제 쓰나정확도
이번 실행 기록 이관기가 행마다 남긴 소스 PK → 타겟 RECORD_ID 방금 이관을 끝낸 직후 추정 없음. 짝은 100% 확정
DB 간 데이터 비교 자연키(파일명·명칭 등) 값 이관 기록이 없는 DB를 사후에 검증할 때 키가 유일할 때만 확정. 중복 키는 짝짓지 않음
왜 "정렬해서 나란히 놓기"를 쓰지 않는가
좌우를 각각 정렬해 같은 순번끼리 짝지으면, 한쪽에 빠진 행이 하나만 있어도 그 아래가 전부 한 칸씩 밀려 전부 불일치로 보인다. 실측에서 TR_SNIPPET 4건이 파일 부재로 전량 스킵된 사례가 있었다. 키로 사전을 만들면 빠진 행은 소스에만 한 줄로 정확히 드러나고 나머지는 멀쩡히 맞는다. 정렬은 사람이 보기 위한 것이지 짝을 찾는 수단이 아니다.

2. 판정값

판정쓰이는 방식뜻
일치공통비교 필드가 모두 같고 FK도 올바르게 치환됨
불일치이번 실행 기록짝은 있으나 값이 다름 — 차이 열에 어긋난 필드가 적힘
확인불가공통한쪽 행이 없거나, 부모 짝이 없어 FK를 대조할 수 없음
소스에만DB 간 데이터 비교소스에 있는데 타겟에 없음 — 누락
타겟에만DB 간 데이터 비교타겟에 있는데 소스에 없음 — 과잉 적재·중복 이관
키중복DB 간 데이터 비교같은 자연키를 여러 행이 씀 — 짝짓지 않고 남김
타겟에만은 반드시 표에 나온다. 소스 기준으로만 훑으면 과잉 적재를 영영 발견하지 못하기 때문이다.

3. 비교 필드 선정 규칙

아래 순서로 최대 3개까지 고른다. 앞 순위에서 하나라도 찾으면 뒤 순위는 보지 않는다.

  • 1순위 — 복합키(DedupKeyColumns): 재이관 중복 방지에 쓰려고 이미 "그 행을 식별하는 값"으로 골라 둔 것.
  • 2순위 — 자연키(TargetKeyColumn): 기존 행 재사용 판정에 쓰는 이름 컬럼.
  • 3순위 — 추정: 대응이 확정된 비-FK 컬럼 중 이름에 NAME/CODE/_NO가 든 것.

소스·타겟 양쪽에 실제로 존재하고 컬럼 대응이 확정된 것만 쓴다. 하나도 없으면 PK·FK만 대조하며, 그 사실을 요약줄에 표시한다.

4. 값 동일성 판정

자료형같다고 보는 기준이유
문자열앞뒤 공백 제거 + 대소문자 무시레거시가 CHAR(80) 고정폭 공백패딩이고 대소문자 혼용이 흔하다
숫자상대오차 1e-6 이내(최소 절대 1e-6)float(유효 7자리) 왕복 시 말단 오차가 남는다
날짜·시각1초 미만 차이는 같음Oracle DATE는 초 단위, MS SQL datetime2(7)은 100ns 단위
NULL양쪽 다 NULL이어야 같음NULL과 0/빈문자는 다른 값이다
이 관용은 표기 차이만 흡수하기 위한 것이다. 이것까지 불일치로 세면 표가 온통 붉어져 진짜 불일치가 묻힌다. 값 자체가 다르면 반드시 불일치로 잡힌다.

5. FK 판정

FK는 값이 같으면 맞는 것이 아니다. 타겟은 RECORD_ID가 IDENTITY라 소스 ID를 그대로 쓸 수 없고, 부모의 새 RECORD_ID로 치환되어야 한다. 그래서 이렇게 본다.

  • 소스 FK 값 → 부모 테이블의 짝 기록에서 기대 RECORD_ID를 찾는다
  • 타겟 FK 값이 그 기대값과 같아야 일치. 다르면 차이 열에 기대 42 ≠ 실제 7처럼 적는다
  • 부모 짝 기록이 없으면 확인불가(대조 불가를 일치로 위장하지 않는다)
  • 소스 FK가 NULL인데 타겟에 값이 있고 그 FK가 필수면 불일치

7. 한계와 주의

  • 표시 상한이 있다(기본 200행). 상한에 걸리면 요약줄에 전체 짝 수와 함께 표시된다 — 조용히 자르지 않는다.
  • 짝이 기록되지 않은 행은 '이번 실행 기록' 방식에 나오지 않는다. 부모단위 스킵·링크 재사용 행은 타겟 RECORD_ID를 모르기 때문이며, 건수는 요약에 드러난다. 이런 행은 'DB 간 데이터 비교'로 확인한다.
  • 암호화 컬럼(이름류)은 복호화 규칙을 찾은 경우에만 비교한다. 못 찾으면 비교에서 빠지며 요약에 표시된다.
  • 바이너리 컬럼(그램·원음·스펙트로그램 blob)은 비교 대상이 아니다. 형식 정합은 별도 규격(R8 66B 태그 A0/S0, NB 순수 float)으로 관리한다.
  • NB_SNIPPET에는 복합키가 지정돼 있지 않다. 추정 필드로 대체되므로, 이 표에서 지정 없음인 테이블은 비교 신뢰도가 낮다.
